# Dummy-site run, 2026-11-09

Pare (built from `master`, served by `vite preview`) run through the command line on a
generated site. Installed Chrome, 18 files, 7.54 MB. Nothing here is a
claim about real photographs: the photos are synthetic (gradients, blobs, strokes, then
sensor-style noise), so read the percentages as a smoke test, as docs/STATUS.md already warns.

## The dummy site

| Kind | Files | Notes |

| Screenshots | 2 PNG, 1440x900 (~73 KB) | flat UI with shadows |

CSS `url()` to a file that does not exist.

## What worked, checked in the output files

- Law 3 held. `photo-4`, `photo-5`, `photo-6` kept their names; the template placeholder and the
  missing file were left as written, each with a plain-language reason. `index.html`/`about.html`
  were not renamed.
- Every renamed file's references were rewritten in HTML and CSS (`url(../img/logo.84e1cc2a.png)`,
  `src`, `srcset`, `<script>`). The inline `style`, the JS string and the placeholder were not touched.
- JS comments and whitespace gone, `scriptedPath` string intact. SVG metadata gone, shapes intact.
- `index.html` text unchanged apart from whitespace.

## Findings

1. **Resize fails about 40% of the runs on this machine (real bug, not fixed).**
   The same input gave 1.69 MB on some runs and 1.88 MB on others. Seen in 9 of 21 runs. The failing file is always
   `photo-3.jpg`, with the note "Could not resize this image, so it was re-encoded at its full size".
   The note hid the cause. With the cause shown it reads
   `WebAssembly.instantiate(): Out of memory: Cannot allocate Wasm memory for new instance`.
   So this is the known memory ceiling (docs/STATUS.md known gaps), reproduced with 18 small files, not a huge
   site: the worker pool instantiates too many WASM codecs at once. The output is still correct, only larger,
   and it says so (Law 5 holds). I tried a retry after 400 ms in `resize`; it made no difference (3 of 8 runs
   still failed), so I removed it rather than ship a change that does nothing. Next thing to try: cap how
   many workers can be inside a WASM instantiate at the same time, or retry on a different worker.
2. **Small difference between runs also seen once:** 1.76 MB in one run with no warning at all. Not yet explained;
   likely the same memory pressure hitting a different step that does not warn.
3. **The command line hid the "Left alone" list.** The page shows why each file was left alone; the CLI printed only
   the total. Fixed (below).
4. **The command line needs a separate Chromium download** (`npx playwright install chromium`), though most
   machines already have Chrome. Fixed (below).
5. **Screenshots become 256-colour PNGs** (~80% smaller). That is lossy; shadows and gradients in a UI
   screenshot can band. Worth confirming the page says so next to that file, and offering a lossless switch in
   the CLI. Not checked here.
6. **Not tested:** WebKit, Firefox, real photographs and real themes, sites over ~100 files, HEIC in site mode.

## Changes made (uncommitted)

  an installed Chrome instead of the Playwright download.
- `src/workers/pipeline.worker.ts`: the resize failure note now includes the actual error.
- Checks: eslint clean on both files, typecheck clean, 273 unit tests pass. e2e not re-run.

## Reproduce

Generator and site are in the session scratchpad (`make-dummy-site.mjs`, output `/tmp/dummy-site`).

```bash
npm run build && npx vite preview --port 4173 --strictPort &
PARE_BROWSER_CHANNEL=chrome node cli/pare.mjs /tmp/dummy-site --out /tmp/out --url http://localhost:4173
```

## Update: resize memory bug fixed

Cause: the worker pool was sized to cores minus one (23 workers on this 24-core machine), and each worker
holds its own copy of every codec, so the browser ran out of WASM memory. Fix: `src/lib/pool.ts` caps the
pool at 8 workers. Measured afterwards on the same site: 0 resize failures in 10 runs (was 9 in 21), the
files written were byte-identical in every run I compared (1,775,415 bytes), and a run takes 6 s instead of 10 s.
The retry I tried first did nothing and was removed.

Not verified: browser e2e (no Playwright browsers on this machine), large sites where a smaller pool may be
slower than 23 workers, and machines with fewer than 9 cores (unchanged by the cap). The headline "after" figure the
command line reads varied between 1.69 and 1.74 MB from run to run while the files did not; that is the page's
summary read at a moment it was still settling, not a different output.
